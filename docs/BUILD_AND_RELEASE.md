# Building and releasing WTF-P

WTF-P `0.6` has a source layer and a generated layer. It does not transpile JavaScript, but it is no longer a zero-build package: every native client envelope is compiled deterministically from the portable protocol before testing or publishing.

## Source and generated boundaries

Edit these sources:

- `protocol/actions/`, `protocol/workflows/`, `protocol/roles/`, and `protocol/skills/`
- `protocol/project/` schemas, templates, and URI rules
- `protocol/catalog.json`, `protocol/effects.json`, and `protocol/tools.json`
- `bin/lib/adapter-compiler.js` for host packaging rules
- `bin/lib/manifest.js` and the installer transaction modules for installation behavior

Do not hand-edit files carrying a `Generated by WTF-P adapter compiler` banner. The compiler owns generated files in these envelopes:

| Envelope | Native form |
| --- | --- |
| `vendors/plugin` | Canonical Agent Plugins 1.0.0 bundle, including the Clio projection under `ai.iowarp.clio/` |
| `vendors/claude` | Claude plugin and local marketplace: commands, skill-bound agents, output style, write-guard hooks; plus the same root `plugin.json` and `ai.iowarp.clio/` component graph as `vendors/plugin`, for Clio adoption |
| `vendors/codex` | Codex plugin (portable root with `com.openai` overlay), marketplace, and TOML custom agents |
| `vendors/copilot` | Copilot plugin/marketplace plus copyable `.github` project projection |
| `vendors/opencode` | OpenCode commands, subagents, and skills |
| `vendors/antigravity` | Antigravity plugin: schema-conformant manifest, commands, subagents, skills, rule |
| `vendors/gemini` | Gemini extension: TOML commands, flat agents, skills, context file |

Each envelope contains `.wtfp-generated.json`, which authenticates every compiler-owned path and its SHA-256 digest. Regeneration removes stale paths only when the previous inventory proves compiler ownership. A malformed or traversing inventory fails closed.

## Development commands

```bash
npm run build:adapters       # Regenerate all nine plugin/marketplace envelopes
npm run check:adapters       # Read-only reproducibility check
npm run test:protocol        # Canonical contracts, skills, roles, schemas, compiler
npm run test:tools           # Seven bounded bibliography/citation implementations
npm run test:evaluation      # Routing, semantic-baseline, and lifecycle contracts
npm run test:installer       # Paths, receipts, races, native registration, lifecycle
npm run test:compatibility   # Package structure, content lint, dry-run wiring, feature checks
npm run test:integration     # Isolated end-to-end installer scenarios
npm run test:all             # Everything required before release
```

The test suite must never use a developer's live agent configuration. Tests set `HOME`, XDG roots, temporary directories, and every supported client-specific configuration variable to disposable paths. A failure that writes into a normal Claude, Clio, Codex, Copilot, OpenCode, Antigravity, or Gemini profile is a release blocker.

## Changing canonical behavior

1. Edit the canonical protocol, skill, role, or adapter source.
2. Run `npm run build:adapters`.
3. Review both the source change and generated projections.
4. Run `npm run test:all`.
5. Run `npm run check:adapters` again. It must report no drift.

CI runs `npm test`, whose first step is the read-only adapter check. A contributor cannot make a canonical change while silently leaving tracked host projections stale.

`CONTRIBUTING.md` is also a generator source: it is projected into every envelope as `repository/CONTRIBUTING.md`, so editing it changes all nine inventories.

## Resealing the routing matrix

`evaluation/v1/routing/manifest.json` binds the nine generated inventories by SHA-256 and names the commit (`wtfp_commit`) whose envelopes it seals; `evaluation/v1/baselines/hpc-checkpointing.json` and `test/evaluation-routing-runner.test.js` pin the same identity. Any commit that changes a generated envelope, including a version bump, therefore has to be followed by a reseal commit or `npm run test:evaluation` fails with an inventory drift error.

1. Commit the source change together with its regenerated envelopes.
2. Run the reseal helper against that commit. It rewrites `wtfp_commit`, each envelope's `manifest_sha256` (the digest of the committed `.wtfp-generated.json`) and `source_sha256` (that inventory's `sourceHash`), the baseline's canonical source pair, and the runner test pins, then loads the suite once to confirm the seal verifies:

   ```bash
   node scripts/reseal-evaluation.js HEAD
   node test/evaluation-routing-runner.test.js
   ```

3. Commit the three files as `test(evaluation): reseal the routing matrix on <what changed>`, naming the envelope commit in the body.

Fixture, corpus, and case seals are never touched by this procedure. Running the helper again against the sealed commit is a no-op.

## Package preflight

```bash
npm run preflight
```

Development preflight checks:

- package identity, Node.js floor, binary declarations, and executable bits;
- canonical and native envelope entry points;
- deterministic generation;
- the full unit, compatibility, ownership, and integration suite;
- the actual `npm pack --dry-run --json` allowlist;
- whitespace errors in the Git diff.

The archive check verifies the runtime-critical protocol and seven target entry points are really present. It does not estimate correctness from a file-count regex.

Immediately before registry publication, use the stronger mode:

```bash
npm run preflight -- --publish
```

Publish mode additionally requires a clean tree, an exact `v<package-version>` tag on `HEAD`, and working npm authentication (`npm whoami`). Credentials are checked by npm itself and are never read or printed by WTF-P. Before the tag exists, and on a tree with an uncommitted operator-owned file, expect exactly the clean-tree, exact-tag, and (when logged out) authentication checks to fail and nothing else.

## Version preparation

WTF-P follows Semantic Versioning, including prerelease identifiers. Prepare a release as reviewable repository changes; the release helper deliberately does not invent changelog text or silently bump hundreds of generated manifests.

For example, to prepare a future prerelease, replace the placeholder with the
reviewed SemVer value before running these commands:

```bash
wtfp_release_version='<next-prerelease-version>'
npm version "${wtfp_release_version}" --no-git-tag-version
# Edit CHANGELOG.md and its comparison link.
npm run build:adapters
git diff --check
git add package.json CHANGELOG.md vendors
git commit -m "chore(release): prepare ${wtfp_release_version}"
node scripts/reseal-evaluation.js HEAD
git add evaluation/v1/routing/manifest.json evaluation/v1/baselines/hpc-checkpointing.json test/evaluation-routing-runner.test.js
git commit -m "test(evaluation): reseal the routing matrix on ${wtfp_release_version}"
npm run test:all
```

The version string is embedded in every envelope manifest, so the bump always changes all nine inventories and always needs the reseal. If a lockfile exists, include it in the version-preparation commit. Never use a broad add command without inspecting the worktree; generated adapters can coexist with operator-owned local files. A version whose changelog entry was never tagged or published may be folded into the next entry rather than kept as a phantom release.

## Tagging and publication

Preview the finalization checks:

```bash
npm run release -- --dry-run
```

The helper refuses to tag on any branch other than `main` and refuses a dirty tree. After the reviewed release commit reaches `main`, create a local annotated tag:

```bash
npm run release -- --tag
```

Pushing is a separate, explicit operation:

```bash
npm run release -- --tag --push
```

The helper never runs `npm publish`. After the tag exists:

```bash
npm run preflight -- --publish
npm publish --tag next       # prerelease
# npm publish                # stable release
```

Separating preparation, tagging, pushing, and registry publication keeps each externally visible mutation inspectable and independently authorized.

Run post-publish `npx --package=wtf-p@<version> -- wtf-p ...` checks outside this checkout. When the working directory's own `package.json` already satisfies the requested version, npx skips the download and fails with `sh: 1: wtf-p: not found`. The registry may also take a few minutes to serve a newly accepted version.

## Native validation matrix

Before claiming first-class support, validate the packed artifact in disposable client homes with the currently supported CLIs:

- Claude: strict marketplace/plugin validation, marketplace add, plugin install/list, and discovery of every catalog command and role agent
- Codex: marketplace add, plugin add/list, seven skill discovery
- Copilot: marketplace add, plugin install/list; in-session command/agent/skill discovery when credentials are available
- Clio: `library install`/`inspect`/`remove` on 0.4.7 or newer, package listing
  via `library list --kind plugin --json`, runtime skill listing via
  `library skills --all --json`, recursive `/wtfp:*` prompts, the static
  `/wtfp:help` card, plugin-bound agents, both fleet `validate`/`graph` paths,
  packaged reference containment, scope coexistence, idempotence, disable
  preference retention across repair, and real native install/remove compensating
  rollback on verification failure. Treat the fleets as explicit `fleet run`
  primitives; ordinary `/wtfp:*` prompts do not auto-route through them. Also
  confirm `library inspect` accepts the Claude envelope, since Clio adopts an
  installed Claude plugin through its root manifest.
- OpenCode: configured-directory command, skill, and agent discovery
- Antigravity: plugin validate/install/list
- Gemini: extension validate/install/list

Record the exact commands and their output in `docs/HOST_CAPABILITIES.md`, and mark a projection unverified when its CLI was not available for the run.

### Native Clio test recipe and snapshot evidence boundaries

The reproducible native Clio integration suite is run with an explicit `WTFP_CLIO_ENTRY`:

```bash
TMPDIR=<disposable-tmp> WTFP_CLIO_ENTRY=/path/to/built/clio-coder/dist/cli/index.js node test/clio-native-integration.test.js
```

Evidence requirements and boundaries:
- **Explicit entry and disposable isolation**: The test requires `WTFP_CLIO_ENTRY` pointing to an absolute built CLI file and isolates all profiles, data, state, cache, and scratch directories under disposable roots. It forwards no credentials and makes no model or network calls.
- **Interim frozen snapshot labeling**: Current native verification rests on an interim frozen Clio 0.4.7 built snapshot (entry SHA-256 `97c11656520161dcec48600786ecc128f1ae2cde660e7fb99a6d9f347e3a9f39`, dist digest `13b913e506a34e0532119c2cb27b8d7d38dd52431ca8d3e2ba0805f7313003dc`, source HEAD `b7d9e591` plus uncommitted changes recorded at snapshot creation). This is explicitly **not** a final clean release SHA or final packed-consumer proof from an npm registry build.
- **Status of release gates**: Native integration tests pass with exit 0 (`test/clio-native-integration.test.js` at commit `6f95279`, production installer at `3d9387f`). Final release gates remain open pending settled documentation, final preflight checks, and publication of Clio 0.4.7.

At least one harmless academic fixture must also exercise real Claude, Codex,
and Clio execution without touching normal client state. Keep static lint,
native discovery, local-model, and paid-model evidence as separate levels. Record exact
binary/source hashes, requested and actual model/effort, permission policy,
fixture hashes, cost provenance, profile pre/post hashes, and credential cleanup
in the release evidence; first-class support is an observed compatibility claim,
not merely a valid JSON manifest. Clio compatibility is declared by
`compatibility.clio` in the bundle's `plugin.json` and enforced by the client's
plugin lifecycle.

## CI and release checklist

- [ ] `npm run check:adapters` reports current output
- [ ] the routing matrix is resealed on the last envelope-changing commit
- [ ] `npm run test:all` passes
- [ ] native validators and isolated discovery pass for every advertised target
- [ ] the real-agent fixture passes the exact scope claimed; partial and failed phases are documented without promotion to a full-lifecycle result
- [ ] applicable routing/lifecycle evidence passes its sealed matrix or records an honest capability limitation
- [ ] certifying Clio lifecycle evidence uses `read-only` preview or supervised `suggest` autonomy and fails on every undeclared tool call; exploratory `full-auto` runs are labeled non-certifying because Clio slash prompts do not enforce an action-scoped tool surface
- [ ] both generated Clio fleets validate and execute nested writes without rollback
- [ ] `git diff --check` passes
- [ ] `CHANGELOG.md`, README capability matrix, and migration notes match observed behavior
- [ ] `npm run preflight` passes on the release commit
- [ ] inspect the actual `npm pack --dry-run --json` file list, sizes, and forbidden obsolete paths
- [ ] normal-profile pre/post hashes match and all disposable credential copies are absent
- [ ] the tag is annotated and exactly matches `package.json`
- [ ] `npm run preflight -- --publish` passes before registry publication
- [ ] a fresh install from the published tarball passes in disposable homes

Reserve `1.0.0` for a fully observed compatibility matrix with no unresolved high-severity ownership or data-loss defect.
